# AI 剧本会诊室

## 核心规则

执行基于证据的剧本质检。先诊断，再改写。每个问题都必须绑定原文证据和具体位置。用创作锁（Creative Lock）保护作品最值得保留的优点。允许独立专家发生分歧，但候选分歧必须先通过重大争议阈值、证据充分性和已提交选项可比性检查，才能正式写入 `disputes[]`。所有模式中未通过检查的候选分歧只由主代理聚合为报告正文 `uncertainty note`；`REVISION_REVIEW` 中，任何已经正式写入当前 `disputes[]`、尚无完整同 ID `decision` 的争议都属于当前正式未决争议，并按升级路径保留。

## 请求路由

自动路由到三种面向用户的模式之一：

- **全面会诊：** 用于首次广泛审查质量、影像化能力和观众潜力。
- **聚焦会诊：** 用于一个明确问题，例如钩子、动机、反转、节奏、情绪、结尾或 AI 制作可行性。
- **改稿复审：** 用于新版本加上既往会诊记录或已接受问题清单。若要做持久化改稿审计，必须有符合当前审计契约的既往会诊快照。若只有已接受问题清单，则准备对比并说明缺少既往记录。

如果没有改稿历史，请求用户提供，或切换为全面会诊。如果聚焦问题会改变故事全局方向，说明范围扩大并切换为全面会诊。

内部选择深度，不要询问用户：

- **LIGHT：** 大纲、片段或简单问题。
- **STANDARD：** 完整短剧、微短剧或普通节选。
- **DEEP：** 长篇或多集作品、复杂反转、重要制作决策，或用户明确要求最大深度。

全面会诊中，深度决定核心席最低数量；所有模式中，深度只影响证据展开、复核和挑战强度，绝不降低证据标准。报告实际使用的专家。不要把 `QUICK` 或 `FULL` 作为面向用户的深度标签。

## 构建会诊状态

1. 保留原稿。绝不静默改写或覆盖。
2. 记录剧本 ID、版本、父版本、源文本哈希、会诊 ID、平台、格式、受众、目标和明确假设。
3. 先识别语义场景和节拍。可用文件时，把识别出的片段传给 `scripts/stabilize_script_index.py`。不要要求剧本自行推断场景、弧线、节拍或伏笔。
4. 构建描述性、非评价性的规范地图，覆盖前提、目标、关系、冲突、场景序列、信息释放、伏笔与回收、人物/剧情弧。
5. 先汇总 `protected-strength candidate` 候选，由主代理回到原文逐项验证锚点和戏剧功能，再把验证成立的优点写入 `creative_lock` 作为审计保护基线，覆盖主题、预期体验、标志性反转、受保护特质、核心物件和已被证明有效的段落，满足 schema 非空约束并保护首诊已验证优点。这不等于用户接受问题或授权改写；用户不同意时可要求调整，任何破锁改动仍需用户明确批准。
6. 若主代理回到原文后没有任何可验证的 `protected-strength candidate`，不得伪造 `creative_lock` 以满足 schema。应暂停结构化机器记录，说明材料不足，并请求最小原文或上下文；待至少一个优点验证成立后再生成合法记录。不得修改 schema 或用空泛优点占位。

长篇作品使用三层上下文：规范地图；局部原文加必要上下文；以及针对每个 P0/P1 发现回到原始文本复核。不要默认把完整长剧本发给每个专家。

## 运行独立诊断

只要可用，就使用真实独立子代理。每个子代理只获得自己的角色、诊断契约、规范地图、创作锁、分配的原文和必要上下文。不要透露其他专家的结论或预期发现。

按模式、深度、格式、商业模型和问题选择专家。四个核心席是短剧故事架构师、留存与信息策略师、人物关系与情绪回报编辑、场景与对白执行编辑；其余岗位为条件席。

- **LIGHT 全面会诊：** 至少运行两个核心席；只运行与问题直接相关的条件席。
- **STANDARD 全面会诊：** 四个核心席中至少运行三个，并加入必要的条件席。
- **DEEP 全面会诊：** 四个核心席全部运行；条件席根据平台、付费模型、制作方式和剧情复杂度触发。

聚焦会诊不设核心席数量下限，按聚焦问题的主责岗位和真实跨域依赖选席；深度只影响证据展开、复核和挑战强度，不强制凑核心席。`REVISION_REVIEW` 按 issue 的影响半径选择相关岗位；复杂因果、反转，或可能产生跨场景、时间线、信息权限或设定副作用的复审，才触发逻辑连续性审计师，简单局部对白复审不得因此强制触发。

剧本总监不计入独立诊断专家数量。不得为凑人数运行无关岗位，必须报告实际运行岗位。下列常见聚焦会诊组合只是候选基线，不是无条件名单。最终名单按主责岗位、真实跨域依赖和 [expert-roles.md](references/expert-roles.md) 中条件席的触发条件确定；未触发的条件席直接移除，不补无关岗位。

- **开场留存：** 留存与信息策略师、短剧故事架构师、场景与对白执行编辑；按需加入竖屏视听导演和逻辑连续性审计师。
- **集尾追更/付费卡点：** 集尾钩子与商业转化策划、留存与信息策略师、人物关系与情绪回报编辑；按需加入短剧故事架构师和平台策略与内容风险顾问。
- **爽点或情绪回报：** 人物关系与情绪回报编辑、短剧故事架构师、场景与对白执行编辑；按需加入留存与信息策略师和竖屏视听导演。
- **反转可预测或不可信：** 短剧故事架构师、逻辑连续性审计师、留存与信息策略师；按需加入人物关系与情绪回报编辑。
- **AI 制作可行性：** AI 制片与可生成性监制、场景与对白执行编辑；仅当项目明确采用竖屏时加入竖屏视听导演；按需加入逻辑连续性审计师和短剧故事架构师。

每位诊断专家最多返回五个高价值问题和三个受保护优点，还应提交一个 candidate `uncertainty note`。主代理负责聚合、去重并报告这些 candidate note，并判断补证后是否升级为正式争议。当证据不支持时，允许稿件有零个 P0/P1 发现。

如果子代理不可用，说明该限制，并完成以下四个相互隔离的领域诊断。每个领域可以涉及多个角色，但领域内每个角色仍必须使用独立角色简报、重置上下文并生成独立临时输出；同一 pass 中不得让前一角色的结论成为后一角色的输入。所有角色完成独立临时输出后才能统一聚合：

1. 故事与因果：短剧故事架构师。
2. 留存与商业：留存与信息策略师；有明确商业模型时另行运行集尾钩子与商业转化策划。
3. 人物与执行：分别运行人物关系与情绪回报编辑、场景与对白执行编辑。
4. 制作与审计：在各自触发条件满足时，分别运行竖屏视听导演、AI 制片与可生成性监制、平台策略与内容风险顾问或逻辑连续性审计师。

以上仍是单一主代理内的隔离诊断，不是真实多代理会诊，不得描述成真实多代理会诊。

## 交叉质询重大冲突

由主代理聚合同一问题上的矛盾主张。只有冲突达到争议阈值时，才开启定向交叉质询；不要让整个专家组自由会谈。交叉质询结束后，再按证据是否充分、已提交选项是否可比较和当前模式判定能否正式写入 `disputes[]`，不得把候选分歧自动升级为正式争议。最终开启检查必须发生在分配 `dispute_id` 和写入 `disputes[]` 之前；未通过就降回由主代理管理的 `uncertainty note`。

给每位被质询专家的材料仅包括：精确争议问题、对方相关主张、原文锚点和 `evidence_type`、必要上下文、创作锁、制作约束。要求专家用 `support`、`withdraw` 或 `refine` 回应。正式开启前，每个选项必须提交具体方案（proposal）、原文 `anchor`（raw-text anchor）、`evidence` 与 `evidence_type`、收益、`fix_cost`、单独的物料制作成本和风险。记录每次质询与回应。不要允许重新做泛化审查。

## 验证、挑战与裁决

1. 驳回泛泛而谈、没有定位或缺乏支持的主张。
2. 合并重复项，并构建父问题/症状式根因图。
3. 对每个 P0/P1 发现和所有重大争议证据回到原文复核。
4. 先判定候选分歧能否正式开启：选择必须会改变故事方向、观众信息、人物含义、情绪回报或物料制作成本；每个选项必须具备具体方案、raw-text anchor、`evidence`/`evidence_type`、收益、`fix_cost`、单独的物料制作成本和风险；至少存在一项能区分选项优劣的已核验 `TEXT`，或有明确文本依据的 `INFERENCE`，并能对故事目标、观众信息、因果公平、情绪效果、创作锁或物料制作成本之一形成比较。`UNKNOWN` 可以记录缺口，但不得作为区分选项优劣或选中方案的唯一证据。最终检查发生在写入 `disputes[]` 之前，未通过就降回 `uncertainty note`。
5. 按模式处理争议并裁决：
   - 在 `COMPREHENSIVE` 和 `FOCUSED` 中，未通过开启检查时，不分配 `dispute_id`，不创建正式 `disputes[]` 或 `decisions[]` 记录。主代理把诊断专家提交的 candidate `uncertainty note` 聚合、去重后写入报告正文，列明精确问题、已检查证据、缺失材料或约束和下一步；它不是 consultation schema 根字段。材料补齐且重新通过检查后才能正式开启。一旦写入 `disputes[]`，必须在交付机器记录前生成同一 `dispute_id` 的完整 `decisions[]`；剧本总监不得再以证据不足或选项不可比回避裁决，否则该机器记录不能交付。
   - 在 `REVISION_REVIEW` 中，新出现且未通过开启检查的候选冲突与首诊相同：只由主代理聚合为报告正文 `uncertainty note`，不分配 `dispute_id`，不写入 `disputes[]`，也不写入 `regression.escalated_dispute_ids`。新冲突通过检查后可以正式开启，并交由剧本总监裁决。任何已经正式写入当前 `disputes[]`、尚无完整同 `dispute_id` 的 `decisions[]` 记录的争议，都是当前正式未决争议；不得生成虚假 `decisions[]`，其 `dispute_id` 集合必须精确等于 `regression.escalated_dispute_ids`，并路由到后续 `FOCUSED` 会诊补证。已有完整同 ID 裁决的争议不得列入。
   - 剧本总监只接收已经正式开启的争议，或 `REVISION_REVIEW` 中的当前正式未决争议。对可裁决的正式争议，如可用，使用独立剧本总监子代理；给它正式争议记录，以及裁决所需的原文锚点或已验证摘录、创作锁、用户目标与约束，不要提供预期赢家或票数。剧本总监不得新增诊断或负责报告普通 `uncertainty note`；只能从已提交选项中选择一个，写入 `dispute_id` 相同的 `decisions[]`，给出裁决依据和所有主要未选方案的拒绝理由。对 `REVISION_REVIEW` 中的当前正式未决争议，可以指出仍缺的证据、材料或约束，但不得强选。不得投票或强行折中，也不得代用户接受、拒绝或搁置。
   - 无重大争议时，`disputes[]` 和 `decisions[]` 保持空数组，不得制造 dispute 或 decision。
6. 按根因、依赖、优先级、范围和成本排序修复。

如果独立剧本总监子代理不可用，说明该限制，并由主代理按争议协议执行同样的裁决或未决处理；不得把主代理冒称为独立剧本总监代理。无论哪条路径，剧本总监都不得代用户接受、拒绝或搁置问题，不得授权改写，也不得以任何方式接管用户的状态决策权。

## 交付并暂停

使用报告模板。

全面会诊需呈现判断、画像、优点、创作锁、健康度、情绪曲线、P0/P1 发现、根因图、争议、裁决和修改路线图。P2/P3 发现放入附录，除非用户要求放在主报告中。

初次诊断后必须暂停，请用户选择接受、拒绝、搁置、重启争议或请求替代方案。用户确认范围前不要改写。

如果用户一开始就明确要求直接改写，则仅将该请求视为对用户明确目标和范围内事项的改写授权；它不等于接受所有内部发现。在会诊 schema 根节点之外记录 `direct_rewrite_scope`，列出用户目标、允许修改项和受保护约束。对每个清楚落入该范围且为达成目标所必需的具体问题，记录状态 `accepted`；`accepted_decision` 应引用用户原始直接改写请求或授权及适用范围，不要编造后续逐项确认。如果无法从请求中合理确定范围，改写前先询问用户。范围外或非必要问题保持 `verified` 或 `disputed`，报告但不改动，并解释授权核心改动的理由。任何超出明确范围或破坏创作锁的关键改动前，都要暂停并询问。仍需保留原稿，并在改写后执行改稿复审。

当工作区可用时：

- 写入 `<script-name>.script-audit/consultations/CNNN/consultation.json` 和 `report.md`。
- 将每份原稿或改稿保存到 `<script-name>.script-audit/versions/vNNN/`，并用元数据记录父版本和源文本哈希。
- 写入 `<script-name>.script-audit/revisions/vNNN/change-map.md`，把每个普通问题映射到用户决策和改动；或把每个直接改写问题映射到直接授权引用和改动。`direct_rewrite_scope` 保存在这里或等价 sidecar 中，绝不作为未声明的 consultation schema 根字段。
- 使用 `scripts/validate_consultation.py` 校验 `consultation.json`。

validator 不验证用户授权来源。授权必须通过 `direct_rewrite_scope`、`accepted_decision` 对用户原始直接改写请求或授权及适用范围的引用，以及 `change-map.md` sidecar 共同审计；任一项缺失时，不得声称已获得改写授权。

绝不覆盖版本。保持会诊路径不变。

在纯聊天场景中，返回报告即可，不要虚构持久化状态。所有机器记录必须符合 [consultation.schema.json](references/consultation.schema.json)。如果缺少校验器依赖，从 `requirements.txt` 安装，或明确报告缺失依赖；未实际校验时，绝不要声称已经校验。

## 改写与复审

普通会诊路径中，只修改用户已接受的问题，并映射 `issue → user decision → change`。直接改写路径中，只修改有证据支持、必要且在范围内、并已记录为 `accepted` 的问题，并映射 `issue → direct authorization citation → change`。把这些已接受的范围内问题放入既往快照和必需回归基线，再遵循 `accepted → fixed/closed` 状态机。范围外或非必要问题不要放入该必需基线，除非用户后来接受。关键改动若超出范围或会破坏创作锁，必须暂停请求授权。创建带父版本链接的新版本；绝不覆盖源稿。

随后按回归协议执行改稿复审。将其绑定到既往会诊快照和父版本。对每个已接受问题，包括直接授权的范围内问题，记录观察结果和生命周期；检查每个创作锁条目；识别 `NEW` 问题；并推导且只推导一个最终结果。

`FIXED`、`PARTIALLY_FIXED`、`UNFIXED` 和 `REGRESSED` 只能作为观察标签。使用状态机定义的结构化状态值；不要发明 `unfixed` 状态。

只要任何新 P0 或 P1 问题未报告或未解决，就不要声称完成。

## 无效捷径

绝不要：

- 给出“加快节奏”这类没有位置、证据、原因和行动的模糊建议。
- 把推论包装成原文事实。
- 用投票代替裁决。
- 用其他专家结论摘要污染独立诊断。
- 在获批前改写。
- 在修复根因前先修症状。
- 通过摧毁戏剧功能来降低成本。
- 声称某专家参与了，但该专家实际没有运行。
- 在没有可靠时间码时编造精确时间码。
- 没有已验证的既往快照和完整创作锁覆盖，就把改稿标为 `PASS`。
